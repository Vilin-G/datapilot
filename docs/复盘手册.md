## 01 · openpyxl 和 pandas 数出来的行数差 1（2026-09-13）

**现象**：同一份 xlsx，openpyxl 的 `max_row` 显示 525,462 / 541,911，pandas 的 `df.shape` 显示 525,461 / 541,910，各差 1。

**原因**：openpyxl 报的是"Excel 里占用的总行数"，**含表头**；pandas 的 `shape` 报的是**数据行数**，不含表头。两个工具统计口径不同，数字都是对的。

**修复**：无需修复。约定：以后说"行数"都明确是"数据行"还是"含表头"。

**教训**：两个工具对同一件事给出不同数字时，**先对齐口径，再怀疑数据**。

**面试可讲**：数据对账时如何定位"数字对不上"——先确认统计口径（含不含表头、含不含空行、去不去重），再查数据本身。

## 02 · to_csv 写在 for 循环外面 → 静默丢掉一半数据（2026-09-13）

**现象**：循环里打印了两次 shape，看起来"两张表都在"；但写文件的语句在循环**外面**。如果不是路径报错，程序会正常退出、只生成一个文件，另一个 sheet 的 52 万行数据无声消失。

**原因**：Python 的循环变量在循环结束后依然存在，df 的值是**最后一次迭代**留下的那张表。写在循环外 = 只处理了最后一张表。

**修复**：把写文件的操作移进循环体内，每张表各写一次。

**教训**：**不报错 ≠ 结果正确**。数据类项目里最危险的不是崩溃，而是"安静地产生错误结果"。每一步都要有产物层面的验收（文件数量、行数、文件大小），不能只看"程序跑完了"。

**面试可讲**：怎么防"静默错误"——关键步骤做产物校验/行数断言，而不是靠肉眼。

## 03 · 把目录当成文件路径 → PermissionError（2026-09-13）

**现象**：df.to_csv(r".../data/processed") 报 `PermissionError: [Errno 13] Permission denied: '.../data/processed'`。

**原因**：to_csv 第一个参数必须是**文件路径**（最后一段是文件名），只给目录等于"往文件夹上写文件"。

**修复**：路径 = 目录 + 文件名 + 扩展名，三部分都要有。

**教训**：读 traceback 从**最后一行**读起——错误类型 + 错误对象；再往上找**第一个属于自己文件的那一帧**，那就是出错的代码行。中间那一堆库内部调用帧先跳过。

## 04 · 逗号写进了引号里 → 文件生成到错误位置（2026-09-13）

**现象**：程序退出码 0，两个 CSV 都生成了、大小也正常（47MB / 48MB），但文件出现在 data 目录下，名字是 "processed, Year 2009-2010.csv"，一看就不对。

**原因**：路径写成了 f".../data/processed, {sheet_name}.csv"——逗号在**引号内**，成了字符串的一部分。这条路径被解析为「目录 data/」+「文件名 processed, Year 2009-2010.csv」。而逗号是 Windows 文件名合法字符，所以系统认为一切正常。

**修复**：要"分成两块"必须让分隔符在**引号外**：

- `Path("目录", "文件名")`（逗号分隔的多个参数）
- `Path("目录") / "文件名"`（斜杠运算符，仅 Path 对象支持）

**教训**：**引号内是数据，引号外才是语法。** 写文件前先 print 出最终路径看一眼——成本 2 秒，能挡住这类错误。

**面试可讲**：一次真实的"程序没报错但结果错"的排查——靠检查产物位置和文件名异常发现。

## 05 · 注释掉的代码 ≠ 保存；没提交到 Git 就等于没写过（2026-09-13）

**现象**：为了"保留复用性"，把已经写对的转换代码注释掉；两天后整段被删掉，代码找不回来了（当时 scripts/ 还是未跟踪状态，Git 里没有任何记录）。CSV 文件还在，但"怎么生成它"的能力丢了。

**原因**：注释掉的代码是最容易被顺手清理的垃圾；而它从未进入版本控制，所以丢失后无法找回。

**修复**：职责不同的代码**拆成不同文件**（转换逻辑独立为 scripts/to_csv.py）；每完成一个可验收的小块就**提交一次**。

**教训**：Git 不是"做完项目再补"的东西，它是唯一的后悔药。提交前先 git status，确认没有大文件混进仓库（原始数据、几十 MB 的 CSV 都不该进版本库）。

**面试可讲**：代码组织（单一职责）+ 小步提交的协作习惯。

## 06 · 把 read_excel 的参数直接套到 read_csv 上（2026-09-13）

**现象**：写 pd.read_csv(xlsx路径, engine="csv") 报错；而 sheet_name 在 read_csv 里根本不存在（会报 unexpected keyword argument）。

**原因**：**函数不同，参数就不同**。参数的差异其实是**文件格式能力的反映**：

- CSV = 纯文本，整个文件就是一张表 → 没有 sheet_name；靠分隔符切列，所以需要 sep
- xlsx = 压缩包容器，可装多张表 → 必须问"读哪张"，所以有 sheet_name；列是单元格结构，所以没有 sep

而 header、dtype、nrows、usecols 属于"表"这个抽象层面的概念，与文件格式无关，所以两者都有。

**修复**：动手前先看签名——help(pd.read_csv)，或 PyCharm 里把光标放进括号按 Ctrl+P。而且记住：**read_csv 最少只需要一个参数：文件路径**，其余等真正遇到问题再加。

**教训**：不要拿一个函数的参数去套另一个函数；先看签名，再写代码。

**面试可讲**：从文件格式差异推导 API 差异，而不是背参数表。

## 07 · 数据落地：xlsx → CSV，读取从 40 秒降到 1 秒（2026-09-13）

**现象**：pandas 读 43.5MB 的 xlsx（两张表共 106.7 万行）约 **40 秒**；转成 CSV 之后读取只要 **1 秒多**（约 40 倍差距）。

**原因**：xlsx 本质是压缩包 + XML，读之前必须先解压、再解析结构；CSV 是纯文本，可以顺序直接读。任何"读之前要先解包"的格式都会慢。

**修复**：一次性把 xlsx 转成 CSV 落到 data/processed/，之后的开发与调试都读 CSV。

**教训**：开发迭代阶段先把数据落到"便宜、稳定、快"的格式（**数据落地 / data landing**）。按实测算账：40 秒 × 每天几十次调试 = 每天几十分钟纯等待——优化依据是实测数字，不是"感觉挺慢"。

**面试可讲**：用实测数据支撑的性能优化（"读取耗时从 40 秒降到 1 秒"）。

## 08 · 数据集下载：官方源太慢，换镜像（2026-09-11）

**现象**：UCI 原站单连接下载只有 ~15KB/s，43.5MB 需要 40 分钟以上；尝试用 Range 分块并发下载时，连接被服务端中断。

## 09 · 两张表的重叠区间是"完全重复"，不是"只是区间覆盖"（2026-09-14）

**现象**：数据被拆成两张按年切分的表，表1 记到 2010-12-09，表2 从 2010-12-01 开始，日期区间重叠 9 天。把这 9 天的数据单独取出来对比：两表各 22,523 行、各 1,088 张发票、共同发票 1,088 张，逐行比较结果**完全相同（True）**。

**原因**：原始数据集按年打包时，两个文件的切分边界没有对齐，导致这 9 天的交易在两个文件里各存了一份完整副本。

**影响**：若直接把两张表合并统计，这 22,523 行会被算两遍（约占总行数 1,067,371 的 2.1%），销量和销售额整体偏高约 2%，而程序不会报任何错。

**修复（第二站执行）**：合并两表时排除重复区间——合并前从表2剔除 2010-12-01~09，或合并后按整行去重（去重前需确认表内是否存在合法的重复行）。

**教训**：

- "日期区间重叠"和"数据重复"是两件事，必须用数据验证，不能靠推测。
- 诊断要发生在改数据之前：先确认是不是重复、重复多少，再决定怎么处理。
- 这类问题最隐蔽——不报错、数字看起来也合理，只能靠主动验证发现。

**面试可讲**：拿到多来源数据先做"重叠/重复检测"，量化影响（22,523 行 / 2.1%）之后再决定清洗策略。

## 10 · 数据入库（SQLite）：一天踩了四个坑（2026-09-16）

**背景**：把 `orders_all.csv`（1,044,848 行 × 8 列）写进 SQLite，得到 `datapilot.db` + `orders` 表。

### 10.1 `sqlite3.connect()` 不传参数 → 建了个内存库

- **现象**：脚本显示运行成功，但 `data\processed\` 里找不到任何 `.db` 文件。
- **原因**：`connect()` 不传参数时默认连到 `:memory:`，数据只活在内存里，程序一结束就消失。
- **修复**：把数据库**文件路径**传进去（`processed_dir / "datapilot.db"`）。
- **教训**：又是"不报错但结果错"。**凡是"写出去/存下去"的动作，结束后必须去目标位置确认产物存在**。

### 10.2 `connect()` 传的是目录 → unable to open database file

- **现象**：`sqlite3.connect(processed_dir)` 报 `unable to open database file`。
- **原因**：SQLite 要的是**文件路径**；传目录等于让它把整个文件夹当成一个数据库文件打开。
- **修复**：路径 = 目录 + 文件名。

### 10.3 连到一个不存在的文件 → SQLite 静默创建一个空库

- **现象**：核对时把库名记错（写成了 `datapilot.db`，当时实际文件叫别的名字），目录里凭空多出一个 0 字节的空库，**全程没有任何报错**。
- **原因**：`sqlite3.connect(路径)` 遇到不存在的文件会**直接创建**，而不是报错。
- **修复**：连库之后第一件事是确认表存在：`SELECT name FROM sqlite_master WHERE type='table'`。
- **教训**：**"连上了"不等于"连对了"。** 数据库工具的这种"宽容"很容易让错误悄悄通过。

### 10.4 断言验错了对象：验了输入，没有验产物

- **现象**：最初写的是 `assert len(df) == 1044848`。看着挺严谨，但**把整段 `to_sql` 删掉，它照样通过**。
- **原因**：`len(df)` 是"读进来的 DataFrame 有多少行"，和"数据有没有真的进库"毫无关系。
- **修复**：改成从库里查——`cur.execute("SELECT COUNT(*) FROM orders")` → `count = cur.fetchone()[0]` → 断言这个 `count`，并且**打印**出来（打印给人看，断言给机器守门）。
- **教训**：**验收必须针对产物本身。验输入等于没验。**

### 附带收获（不是坑，但值得记住）

- **pandas 自动建表**：`df.to_sql()` 根据列名和类型自动生成 `CREATE TABLE`，不用手写建表语句。列名带空格它也照建，但**查询时必须写成 `"Customer ID"`**。
- **`if_exists="replace"` 让脚本幂等**：改完表名重跑，旧表自动消失、新表干净生成——**脚本可以反复运行，每次结果一致**。
- **`parse_dates` 影响库里的类型**：不解析，`InvoiceDate` 建表是 TEXT；解析后是 TIMESTAMP。类型会进入 `get_schema`，直接影响模型怎么理解这一列。
- **缺失值会把整数列变成浮点列**：`Customer ID` 因为 22.5% 缺失，整列是 REAL，整数 ID 显示成 `13085.0`。这不是数据错误，是类型推导的结果。
- **命名是设计**：库名和表名会被 `get_schema` 交给模型看。`library`、`store_1` 这种名字会让模型猜错语义，`orders` 一眼就懂。

**面试可讲**：

- "怎么保证数据写进去了？"——对账查产物（库里 COUNT），而不是"脚本没报错所以应该没问题"。
- "为什么用 SQLite？"——单文件、零运维、这个规模（百万行）完全够用，不用为了简历硬上重型数据库。
- "你的构建脚本能重复跑吗？"——能。`if_exists='replace'` + 行数断言，每次跑都是干净重建，这叫幂等。

## 11 · 写 get_schema：从"能跑"到"能给模型看"（2026-09-16）

**背景**：第二小块的交付物是函数 `get_schema(con)`——把"库里有什么"变成一段**给模型看的说明**。这块的性质和前面不同：前面处理的是数据，这里写的是**给别人用的工具**。

### 11.1 表名写死 → 工具对输入变化不免疫

- **现象**：最初写的是 `PRAGMA table_info(orders)`，表名硬编码在代码里。
- **问题**：库里多一张表、或者换一份数据，这个函数就瞎了——它永远只报 `orders`。
- **修复**：先用 `SELECT name FROM sqlite_master WHERE type='table'` 拿到**表清单**，再循环每一张表分别去查字段、行数、示例。
- **教训**：**一次性脚本可以写死，工具不行。** 工具要对"输入会变"这件事免疫，否则它只是伪装成工具的脚本。

### 11.2 `fetchone()` 和 `fetchall()` 用混了

- **现象**：写成 `con.execute("PRAGMA table_info(...)").fetchone()[1][2]`，报 `IndexError: string index out of range`。
- **原因**：`fetchone()` 只取**第一行**；后面的 `[1][2]` 变成"取这一行的第 2 个元素，再取那个字符串的第 3 个字符"，于是 `cols` 成了一个单字符字符串，后面 `for col in cols` 拿到的自然不是元组。
- **修复**：要取**全部字段**就用 `fetchall()`。
- **教训**：**报错信息里的关键词就是线索**。"string index out of range" 说明当时的对象是个**字符串**而不是预期的元组——顺着这条线就能倒推回 `fetchone()` 用错了位置。

### 11.3 `message = ...` 在循环里被覆盖 → 又一个静默错误

- **现象**：`for table in tables:` 里写 `message = f"..."`，每轮把上一轮的内容**替换**掉。库里只有一张表时，完全看不出来。
- **原因**：`=` 是替换，`+=` / `append` 才是累加。这跟 `03_merge_clean.py` 里 `df` 被写到循环外是同一类问题：**循环里的变量被后面的迭代冲掉**。
- **修复**：容器建在循环**外面**，循环里只做"追加"。
- **教训**：**这类 bug 只在"数据变多"时才暴露**——单表、单文件、单条记录时一切正常。所以验证时要主动构造"多份"的场景。

### 11.4 容器的层级：一个建在循环里，一个建在循环外

- **结构**：`mess`（一张表的所有行）建在**循环里**——每张表都要从空白开始收集；`message`（所有表的段落）建在**循环外**——要跨表累积。
- **教训**：写循环前先问一句——"**这个东西是每一轮独立的，还是要跨轮累积的？**"答案直接决定容器写在循环里还是循环外。同一段代码里两种用法同时存在很正常。

### 11.5 分层拼装：行 → 段 → 全文

- `" | ".join(row)`：把一行数据拼成一行文字（**数字要先 `str()`**，否则报 `TypeError: expected str instance, int found`）
- `"\n".join(mess)`：把一张表的所有行拼成**一段**文字
- `"\n\n".join(message)`：把所有表的段落拼成**一整篇**文档
- `join` 的语义：**在元素之间插分隔符**——N 个元素得到 N−1 个分隔符，所以 `"\n\n"` 意味着"段与段之间空一行"
- **一个反直觉的现象**：库里只有一张表时，`"\n\n"` 根本不会出现——因为只有一个元素，**一个分隔符都不会插**。想验证它真的起作用，就得让数据变成"两份"。这正好印证 11.3 的教训：**要主动制造"多份"的场景**。

### 11.6 验收标准变了

- 前面每一小块的标准是"**脚本能跑出正确结果**"。
- 这一块的标准是"**一个从没见过这份数据的人（或模型），只看这段输出就知道库里有什么**"。
- **教训**：**工具的输出就是它的产品。** 内部实现可以复杂，出口必须干净、能被别人直接使用——所以最后 `return` 的是一整个字符串，而不是一堆元组或嵌套列表。

**面试可讲**：

- "为什么这个函数用循环而不是直接写表名？"——工具要对输入变化免疫，库里多一张表不该改代码。
- "你怎么发现循环变量被覆盖的？"——单表测不出来，我特意造了一张临时表让问题现形；这类 bug 只在"数据变多"时才暴露。
- "为什么输出是纯文本而不是 JSON？"——第一读者是模型，纯文本最直接；需要程序处理时再考虑结构化。
- "输出格式你怎么定的？"——先问"谁读它、读它做什么"，再决定形态。

## 专题 · `join` 到底在做什么（2026-09-16）

**背景**：写 `get_schema` 时用到三处 `join`，连着问了四个问题，这里一次记清楚。

### 问题 1：`" | ".join(row)` 为什么分隔符在中间，而不是开头？

**答**：`join` 的规则是"把分隔符插在**元素之间**"，不是"加在元素前面"。

写法上 `" | "` 出现在点号左边，只是因为语法规定"方法跟着对象写"——**代码的书写顺序和输出顺序没有关系**。

```
" | ".join(row)
└─胶水─┘└─砖块─┘

row = ["A", "B", "C"]
等价于  "A" + " | " + "B" + " | " + "C"
结果    "A | B | C"
```

**N 个元素 → N−1 个分隔符。** 只有一个元素时，一个分隔符都不会插：

```python
print(" | ".join(["A", "B", "C"]))   # A | B | C
print(" | ".join(["A"]))             # A        ← 只有一块砖，没地方抹水泥
print(repr(" | ".join([])))          # ''
```

### 问题 2：`message.append("\n".join(mess))` 也是在元素之间加回车吗？

**答**：对。这一步把 `mess` 里每个元素（一张表的每一行）用换行粘起来，得到**一段多行文字**。

两个附带结论：

- **末尾不会有换行**——`join` 只在"之间"插，所以最后一行后面是干净的。想让每段结尾也空一行，得自己手动加。
- "行"变成"段"，就是这一步的功劳。

### 问题 3：`return "\n\n".join(message)` 就是返回一个用两个回车粘起来的大字符串？

**答**：对，返回的是**一个字符串**（不是列表）。可以用 `type()` 自证：

```python
print(type(result))     # <class 'str'>
```

`"\n"` 和 `"\n\n"` 的区别：

| 写法 | 效果 |
| --- | --- |
| `"\n"` | 换行，下一行紧挨着 |
| `"\n\n"` | 换行两次 = **空一行**，视觉上把两块分开 |

### 问题 4：为什么输出里看不到那两个回车？

**答**：因为**库里只有一张表**，`message` 里只有一个元素——N 个元素才有 N−1 个分隔符，**一个元素就是零个分隔符**。

想亲眼验证，给库里临时加一张表：

```sql
CREATE TABLE tmp_test (a TEXT);
-- 跑一次 06_db_tools.py：会看到两段，中间空一行，tmp_test 那段只有字段、没有样本数据
DROP TABLE tmp_test;
```

### 小结：三个层级，同一个动作

```
sample 的每一行     → " | ".join(row)         → 一行文字
这一张表的所有行    → "\n".join(mess)         → 一段文字（一张表的说明）
所有表的段          → "\n\n".join(message)    → 一整篇文档（一个字符串）
```

- `join` 只干一件事：**在元素之间插分隔符**。"胶水"是什么，决定用什么空白
- **分层的意义**：段内用单换行、段间用双换行——如果只拼一层，就没法区分这两种空白
- **两个自证工具**：`repr()` 看字符级真相（`\n` 会原样显示，不真换行）、`type()` 看返回的到底是什么

**通用思维**：写循环和拼字符串时，先问自己"**我现在处理的是哪一层？**"——行、段、全文，每一层各有一个容器、各做一次 `join`。把层次想清楚，`\n` 和 `\n\n` 就不会用错。

## 12 · 写 run_sql：安全边界、兜底，和一次结构合并（2026-09-17）

**背景**：`run_sql(con, sql)` 是项目里第一个"带安全边界的工具"，三条要求：只允许 SELECT、限制返回行数、出错不崩且原样返回错误。**它将来要交给模型调用**，所以这三个约束不是锦上添花，而是模型能安全干活的前提。

### 12.1 `in` 有三种含义，我滑了三次

- **现象**：三次写出 `if not sql.strip().upper() in ["LIMIT"]`，本意是"语句里没有 LIMIT"，实际含义是"整句 SQL 不等于字符串 LIMIT"——条件几乎永远为真，于是限制逻辑全部失灵。
- **原因**：`in` 的含义取决于右边是什么：
  - `"abc" in "xxabcxx"` → 查**子串**
  - `"abc" in ["xx", "abc"]` → 查**列表成员**
  - `"SELECT ..." in ["LIMIT"]` → 拿整句和列表元素比，永远 False
- **修复**：`if "LIMIT" not in sql.strip().upper():`
- **教训**：**`in` 问的是"在不在里面"，不是"等不等于"。** 先看右边是什么类型，才知道它在查什么。

### 12.2 只读校验：它不是真正的安全边界

- **做法**：`sql.strip().upper().startswith("SELECT")`，不通过就拒绝。
- **定位**：拦住"明显不是查询"的语句（`CREATE` / `DELETE` / `DROP`），**但不是安全防线**——字符串检查挡不住分号拼接、注释、大小写变体这类花招。
- **意外发现**：测 `SELECT * FROM orders; DROP TABLE orders` 时，数据库自己报 `You can only execute one statement at a time.` —— `execute()` 一次只接受一条语句。**但这是 SQLite 的护栏，不是我们的设计**；换数据库或用 `executescript()` 就没有了。
- **真正的做法**（暂不做，记着）：**以只读方式打开连接**（`file:...?mode=ro`），物理上写不进去，SQL 写得多花都无效——这才是最小权限原则的落地。

### 12.3 异常不是"条件"，写不成 elif

- **现象**：想加 `elif 系统报错:` —— 写不出来。
- **原因**：`if / elif / else` 判断的是**条件的真假**；"报错"是执行某行时**抛出来的东西**，只能由 `try / except` 接住。两套机制不能互换。
- **修复**：类型检查、只读检查、执行 SQL 全放进同一个 `try`，`except Exception as e` 统一返回 `{"ok": False, "error": str(e)}`。
- **教训**：**错误文本要原样返回，不要美化。** 第二站的模型要靠这句报错判断错在哪、然后改 SQL；翻译成"查询失败，请检查"就等于毁掉它的线索。

### 12.4 返回形状必须统一

- **现象**：一开始成功返回裸列表、失败返回 dict。调用方没法用同一套代码处理两种结果——`result["rows"]` 在成功时会报 TypeError，`for row in result` 在失败时会把字典的键当数据遍历。
- **修复**：成功 `{"ok": True, "rows": [...], "truncated": ..., "total": ...}`；失败 `{"ok": False, "error": "..."}`。
- **教训**：**形状不一致时，出错方式往往不是崩溃，而是静默地做错事。**

### 12.5 兜底：位置在出口，条件是无条件

- **定义**：不管前面发生了什么，函数返回的数据永远不超过 `max_rows`。
- **三个特征**：① 在 `return` 之前；② **无条件执行**，不挂在任何 if 分支里；③ 让"不超过上限"成为一条永远成立的保证。
- **踩过的坑**：最初把切片挂在"我加过 LIMIT"的分支里，另一条分支完全没切。结果模型写 `SELECT * FROM orders LIMIT 1000` 时，**1000 行原样溜出去**，还标着"没截断"。
- **一句话**：**同一个函数里有几个 `return` 出口，兜底就会漏掉几个之一。** 想让兜底无条件，先让出口只剩一个。
- **它保的是谁**：兜底**不省资源**（数据已经取回内存了），它保的是**下游**——不让 104 万行流进模型、接口和日志。
- **真正省资源的是"取之前就限制"**：SQL 里加 LIMIT，或者用 `cursor.fetchmany(n)`（只取 n 行，剩下留在数据库那边）。后者更优雅，因为不用给 SQL 动手术。

### 12.6 `total` 要在切片之前取

- **现象**：`total = len(rows)` 写在切片之后 → 永远等于 `max_rows`，报出来的总数是假的，而且是**静默错误**。
- **另一个发现**：加了 `LIMIT 100` 之后，数据库只给你 100 行，**你根本无法知道真实总数**。所以 `total` 的真实含义是"我这次拿到了多少行"。

### 12.7 结构合并：从"两个出口"到"一条流水线"

**合并前**（三个 `return`、判断写死、两处重复）：

```python
if "LIMIT" not in sql.strip().upper():
    sql = sql.strip() + f" LIMIT {max_rows}"
    first_back = cursor.execute(sql).fetchall()
    second_back = first_back[:max_rows]
    return {"ok": True, "rows": second_back, "truncated": True, "total": len(first_back)}
else:
    first_back = cursor.execute(sql).fetchall()
    second_back = first_back[:max_rows]
    if len(first_back) > max_rows:
        return {"ok": True, "rows": second_back, "truncated": True, "total": len(first_back)}
    else:
        return {"ok": True, "rows": second_back, "truncated": False, "total": len(first_back)}
```

**合并后**（执行一处、出口一处、判断算出来）：

```python
if "LIMIT" not in sql.strip().upper():
    sql = sql.strip().rstrip(";") + f" LIMIT {max_rows}"

first_back = cursor.execute(sql).fetchall()
total = len(first_back)
second_back = first_back[:max_rows]
return {"ok": True,
        "rows": second_back,
        "truncated": total > max_rows,
        "total": total}
```

**关键区别**：合并前是"`if` 决定走哪条路，两条路各写一遍"；合并后是"`if` 只改原料，加工完大家走同一条流水线"。

**教训**：

- **`if` 可以负责加工数据，但不该决定"有几个出口"。**
- 出口只剩一个之后，兜底才可能真正无条件——**结构决定了你能不能写出正确的逻辑**，不只是好不好看。
- 顺带一个小坑：拼 LIMIT 前要 `.rstrip(";")` 去掉末尾分号，否则 `SELECT ...;` 会变成两句。**模型生成的 SQL 经常以分号结尾**，这个坑早晚会撞上。

**面试可讲**：

- "你怎么保证模型不能改数据？"——三层：只检查 SELECT 开头（拦明显的）、连接以只读方式打开（物理拦截）、限制返回行数（防下游被拖垮）。
- "为什么错误信息不翻译？"——它是模型自我修正的输入，翻译等于毁掉线索。
- "你的工具函数为什么只有一个 `return`？"——返回值只有一个出口，兜底逻辑才可能无条件执行。
- "怎么防止一次查询把内存打爆？"——SQL 层加 LIMIT 省资源，出口再切一刀防漏，并如实标注 `truncated`。

## 13 · 第一站 SQL 验收：三道题里踩出的八个点（2026-09-18）

**背景**：第一站的最终验收是**手写 SQL 回答三道业务问题**（Q1 国家订单数 / Q4 单日订单高峰 / Q5 某商品两段销售额对比）。产出见 `docs\SQL验收.md`。这一节记的是过程中真正学到的东西。

### 13.1 `COUNT` 和 `SUM` 是两件事

- **现象**：写 `COUNT(Quantity * Price) AS prices`，想算销售额，实际得到的是"有多少行"。
- **危险之处**：列名叫 `prices`、数字看着也合理（几千），**看起来完全像对的**——又是静默错误。
- **修复**：算金额用 `SUM`；`COUNT` 是数个数。
- **怎么自查**：① 看数量级（头部商品的销售额应该是十万量级，不是几千）② 交叉验证（单独查一个商品，换个写法看结果是否一致）
- **教训**：**看别人的 SQL，第一件事是核对每一列到底在算什么。**

### 13.2 SQL 子句的顺序是固定的

- **现象**：把 `WHERE` 写进了 `SELECT` 的括号里，连改三次都错。
- **正确顺序**（背这一个模板就够）：

```sql
SELECT   列
FROM     表
WHERE    行的过滤条件
GROUP BY 分组
HAVING   分组后的过滤（WHERE 是分组前）
ORDER BY 排序
LIMIT    条数;
```

- **读法**：从哪张表 → 只要哪些行 → 按什么分组 → 怎么排 → 要前几条。
- **小技巧**：报错常是 `near "XXX": syntax error`，看到 `near` 后面跟着关键字，第一反应就是"这个关键字放错位置了"。

### 13.3 非商品代码会污染排行榜

- **现象**：按销售额排商品，前三名是 `M`（手工调整）、`22423`（真商品）、`DOT`（邮费）。
- **影响**：不做清洗，**"最畅销商品"这个结论就是垃圾**，而且程序不会报错。
- **教训**：商品维度的分析前必须先排除 `M` / `DOT` / `POST` / `BANK CHARGES` 这类非商品代码；**数据质量直接决定结论质量**。

### 13.4 口径不同，结论就不同

- **退货算不算**：同一个商品第一段含退货是 163,051.46，排除退货是 170,078.51，**差 7,027（约 4%）**。
- **区间等不等长**：两段分别是 374 天和 365 天，直接比总额对段2 不公平 → 总额口径 −5.3%，日均口径 −3.0%。
- **教训**：**做对比之前先把口径写死**（退货怎么算、时间窗取哪段、比总额还是日均），否则数字无法复现，讨论也没法收敛。写结论时必须注明口径。

### 13.5 查询给数字，分析要看分布

- **现象**：Q4 找到冠军日 2010-11-04（219 张订单）后，再按国家拆解，发现其中 **207 张来自英国（94%）**。
- **含义**："这是订单高峰日"其实是"英国在这天是高峰"——只看总数会把**局部现象当成全局规律**。
- **教训**：拿到一个"冠军"数字后，多问一句"**这是谁贡献的？**"。拆维度是防止误判最便宜的手段。

### 13.6 会拆比会合重要

- **现象**：用子查询把"找出冠军日 + 按国家拆解"合成一句，跑通了，但两个隐患：① 子查询没写 `LIMIT 1`，能跑只是因为 **SQLite 在需要单值的场合隐式取第一行**（数据库宽容 ≠ 可靠写法）；② 出错时分不清是哪一步的问题。
- **修复**：拆成两句简单 SQL，结果完全一样。
- **教训**：**复杂的 SQL 先拆开写**，验证每一步的结果，再决定要不要合并。拆开的版本更好读、更好调、也更好讲。**依赖隐式行为的地方要写成显式的**。

### 13.7 交叉验证要成为习惯

三道题分别用了不同的交叉验证方式：

- Q1：分组结果 43 行 ↔ `SELECT DISTINCT Country` 43 个；43 个国家订单数加总 53,628 ↔ `COUNT(DISTINCT Invoice)` 53,628
- Q4：冠军日总数 219 ↔ 各国拆分后之和 219
- Q5：含退货/不含退货两版对比，量化出口径影响

**教训**：数字"跑出来了"不等于"对了"。**能用两条独立路径得到同一个数字，才叫可信。**

### 13.8 复合题的正确姿势：拆成小步

Q5 一开始看着很难，拆开只有三步：

1. 挑对比对象（按销售额排商品，注意排除非商品）
2. 分别算两段的销售额（口径写死：时间窗 + 退货 + 商品定位字段）
3. 对比，算增长率

**教训**：复合题不是"写一句复杂的 SQL"，而是"**把一个大问题拆成几个小问题，一次只写一个小查询**"。这一步做完，后面第三站的模型分派任务逻辑其实是同一个思路。

**面试可讲**：

- "你的分析口径是什么？"——退货怎么算、时间窗怎么取、比总额还是日均，一开口就要说清。
- "怎么验证结果可信？"——交叉验证 + 量级自查 + 拆维度看构成。
- "为什么先拆再合？"——可调试、可解释；复杂 SQL 出错时定位成本高。
- "数据质量怎么影响结论？"——非商品代码混进排行榜的例子最直接。

## 14 · 把函数包成工具：`con` 从哪来、输出该长什么样（2026-10-26）

**背景**：第二站第 1 小块。目标是把第一站的 `get_schema(con)` / `run_sql(con, sql)` 变成模型能看见的**工具**——模型得知道有这么两个工具、叫什么、填什么参数。这一小块不执行、不调模型，只到"打印出模型看到的工具清单"为止。产物：`scripts\07_tools.py`。

### 14.1 `con` 不是"固定搭配"，它是一个值

- **现象**：卡了很久，原话是"我以为 con 只是一个使用方法前的固定搭配"。
- **原因**：`con` 这个名字太像关键字了（convention / connection 的缩写，全世界都这么叫）。但它跟 `i`、`df`、`row` 一样，**只是个变量名**，里面装着一个 `sqlite3.Connection` 对象。
- **三个自证**：
  - `x = con; x.execute(...)` 照样跑 → 说明它只是普通对象，不是语法
  - `def show(c): c.execute(...)` → `show(con)` 能跑 → **只要是个值，就能当参数传**
  - 两次 `sqlite3.connect()` 得到 `con is con2 == False` → 两个独立对象
- **教训**：分不清"这是语法还是值"的时候，做一件事就够了——**给它换个名字试试**。换名还能跑，它就是值。
- **面试可讲**：讲工具封装时，先讲清"模型手里只有字符串，碰不到你进程里的对象"，这是理解 function calling 的第一道门。

### 14.2 设计题：`con` 藏在哪儿

模型填不出一个连接对象，它只能填字符串。所以 `run_sql(con, sql)` 这个两参数函数，不能直接交给模型。三个方向：

| 方向 | `con` 藏在哪 | 评价 |
| --- | --- | --- |
| A | 全局变量，谁都能拿 | 最省事，但多用户/多线程会打架 |
| B | 外壳函数肚子里 | 最好懂：`def query_database(sql): return run_sql(con, sql)` |
| C | `functools.partial` 预先绑上 | 最省代码，但对新手最不直观 |

- **实际选择**：B（外加 `con` 在模块顶部建一次）。
- **本质**：`con` 不是被"拎出来"给模型，而是**被包进一个只露 `sql` 的壳里**。模型永远碰不到 `con`。
- **验收方式**：打印 `query_database.args`，确认参数表里**只有 `sql`**。这就是"模型看不见 con"的产物级证明。

### 14.3 文件名以数字开头 → 普通 import 写不了

- **现象**：`import 06_db_tools` 报 `SyntaxError: invalid decimal literal`。
- **原因**：Python 的标识符不能以数字开头，`import` 后面的东西必须是合法标识符。
- **修复**：用 `importlib`：

```python
sys.path.insert(0, str(project_root / "scripts"))
db_tools = importlib.import_module("06_db_tools")
```

- **教训**：文件名是**字符串**，模块名是**标识符**，两者规则不同。`import` 吃的是标识符规则。
- **注意**：`sys.path.insert` 必须写在 `import_module` **之前**，否则找不到文件。

### 14.4 `try/except` 包了一个不会炸的东西 → 死代码

- **现象**：写成

```python
result = db_tools.run_sql(con, sql)
try:
    return result          # 返回字典，永远不会抛异常
except Exception as e:
    new_result = json.dumps(result, ...)   # 永远进不来
    return new_result
```

- **原因**：`run_sql` **内部已经把异常接住了**，失败时返回 `{"ok": False, "error": ...}`。所以 `result` 无论如何都是正常字典，`return` 它不可能炸 → `except` 是死代码。
- **和 12.3 的关系**：12.3 是"想用 `elif` 接报错"（异常不是条件）；这一条是反方向——"用 `try` 接一个已经被接住的报错"（没有异常可接）。**同一个认知盲区的两面。**
- **判断口诀**：问自己"**这时候有没有东西会炸？**"
  - 调 `run_sql(...)`（已封装）→ 不会炸 → 用 `if`
  - 调 `con.execute(...)`（原始）→ 会炸 → 用 `try`
- **教训**：**异常处理不是"保险丝"，包在不炸的代码外面就是噪音。** 它还会骗人——看着像做了错误处理，其实什么都没做。

### 14.5 `json.dumps(indent=2)` 对表格数据是负优化

- **现象**：成功分支写了 `json.dumps(result, ensure_ascii=False, indent=2)`，输出 307 行。
- **实测对比**（同一个 100 行结果）：

| 写法 | 字符数 | 行数 |
| --- | --- | --- |
| `indent=2` | 3517 | 307 |
| 不加 indent | 1903 | 1 |

- **原因**：`indent` 把**每一行数据的每个值**都拆成独立一行。JSON 缩进是给**嵌套对象**看的（人读代码时有用）；**表格数据是平的**，缩进只会把一行拆成五段，模型反而更难看出"哪些值属于同一行"。
- **教训**：**美化格式要看数据形状。** 嵌套多 → 缩进有用；表格平铺 → 缩进是纯噪音，还烧 token。

### 14.6 同一个工具不能有两种输出方言

- **现象**：成功走 `json.dumps`（`true` / 双引号），失败走 `str(result)`（`True` / 单引号）。模型会同时看到 JSON 和 Python 字典两种表示。
- **修复**：两个分支都用 `json.dumps(result, ensure_ascii=False)`。
- **和 12.4 的关系**：12.4 是"返回形状必须统一"（裸列表 vs dict）；这一条是同一个原则再往前一步——**形状统一了，序列化格式也要统一**。
- **教训**：**工具的输出是它的产品**（11.6 那条）。产品不该今天说中文明天说英文。

### 14.7 一个留给后面的坑：`truncated=False` 不等于"数据完整"

- **现象**：`SELECT Country FROM orders`（104 万行）→ 只返回 100 行，但 `truncated` 报 `False`。
- **原因**：`run_sql` 里有两道限制，`truncated` 只盯第二道（Python 切片）：

```
模型 SQL → [SQL 里自动补 LIMIT 100] → [Python 切片 [:100]] → 返回
                第一道门                 第二道门 ← truncated 只看这里
```

  第一道门已经把数据挡掉了，第二道门 `100[:100]` 什么都没切 → 报 `False`。
- **为什么现在不改**：第一站那个阶段 `truncated` 的语义（"我在出口切了没有"）是准确的。一旦交给模型，语义变成"我看到的是不是全部数据"，**这个语义变化是真跑起来之后才会暴露的**。留到那时改，教学价值最大。
- **教训**：**一个字段的含义会随着使用场景变化。** 交接给下游时，要重新问一遍"这个词对下游意味着什么"。

**面试可讲**：

- "怎么把普通函数变成 Agent 工具？"——关键是**参数表要给模型能填的东西**，连接对象这类运行时依赖必须包进壳里，不能出现在参数表里。
- "你怎么验证工具封装对了？"——打印 `tool.args`，用产物证明参数表里只有 `sql`，而不是"我觉得应该没问题"。
- "工具返回值为什么不用漂亮的 JSON？"——第一读者是模型不是人；`indent` 对表格数据是负优化，实测 3517 字符 vs 1903。
- "错误信息为什么原样返回？"——它是模型自我修正的唯一线索（12.3）。
