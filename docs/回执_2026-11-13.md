### 一条数据口径发现（体现数据素养，建议写进简历的技术难点）

**这个库里没有「普通退货」。** 负数量行 22,557 条里，19,164 条属 `C` 开头发票（取消单，Price 全 > 0），另 3,393 条非 C 负数量行 **Price 全是 0**（库存报损）。

## 六、下一步路线（2026-11-13 凌晨与用户达成共识）

**目标形态**：类似 RAG，但处理的是表格。用户上传表格 → 系统自己分析、转 SQLite → 用户提问 → 系统写 SQL 并回答。**前端最后做。**

### 核心前提：`con` 重构（必做，且是两条路的共同前提）

现状：`scripts/07_tools.py` 第 14 行 `con = sqlite3.connect(...)` 是**模块级全局变量** → 一个进程只能服务一张表。

重构方向：改成闭包，`make_tools(con)` 返回一组绑定了该连接的工具。

```python
def make_tools(con):
    @tool
    def describe_database() -> str:
        return db_tools.get_schema(con)
    @tool
    def query_database(sql: str) -> str:
        return json.dumps(db_tools.run_sql(con, sql), ensure_ascii=False)
    return describe_database, query_database
```

**关键教学点（用户已理解）**：
- **闭包** = 把变量藏进函数里，而不是摆在模块顶层
- **不能把 `con` 做成工具参数** —— 工具参数是给模型看的，模型不该知道连接对象。**什么给模型、什么不给，是设计界线**
- **谁写**：这块归用户写（核心概念必须自己写一次），我出任务卡

### 阶段路线（顺序不可颠倒）

```
第 A 阶段：con 重构 + FastAPI 接口 + 一页前端     ← 先能被人看见
第 B 阶段：校验 agent                             ← 第一个真多智能体，不需多表，现在就能做
第 C 阶段：Supervisor + 多表路由                   ← 第二个真多智能体，依赖「用户能传多张表」
第 D 阶段：第二个数据集重测                        ← 比 bind_tools 值钱：回答「是不是只对一个库调参」
────────────────────────────────
bind_tools：优先级已降到最低（用户 2026-11-13 决定）
```

### 两个真能拆的多智能体设计（都不是硬凑，各自有实测依据）

**① 校验 agent（第 B 阶段）**
依据：评测里三种失败（编造数字 / 口径漂移 / 举反例被当正答）共同点是「模型自己写、自己算、自己报，没人复核」。
分工：写手 agent 产出 SQL + 数字 → 校验 agent **不看写手的解释，用独立连接独立重算**，对不上就打回重做。
答「去掉会怎样」：去掉就会有 4.89% 那种编造，而且它自己看不出来。

**② Supervisor + 多表路由（第 C 阶段）**
依据：用户选的是「真实版」（多个用户的表同时在线）。跨表问题必须判断该查哪几张表。
答「去掉会怎样」：去掉就要把所有表的 schema 全塞进一个上下文，表一多就装不下（有实测边界）。

**同时明确：不为 multi-agent 这个标签硬拆。** 如果一个任务本来能一气做完，拆成三个 agent 互相打招呼，面试官一问「Supervisor 到底在决策什么」就会暴露。

### 待定项（用户需回答后才能动手）

1. 上传后的表怎么处理 → 用户已选 **真实版**（每个上传文件生成独立库，多 session 并存）
2. 第 A 阶段前三件事的分工 → 建议：`con` 重构用户写；FastAPI 与前端我代写（工程体力活，不是考点）
3. 多智能体引入后评测口径怎么重定（一轮内通过 vs 允许打回重做）→ 第 B 阶段开工前必须定
