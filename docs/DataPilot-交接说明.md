## 3. 教学模式与协作规则（接手必读，优先级高于"把活干完"）

这些是用户明确提出并多次强调的要求：

**关于写代码**

1. **默认不代写业务逻辑**。助手负责：设计任务、解释概念、给提示、做 code review、指出边界情况和坑。用户负责写代码。
2. **例外**：用户明确说"给我代码""你帮我写"时才给。给了也要说明这段代码的关键点，让他能复述。
3. **分级提示三档**：① 方向提示（往哪查）→ ② 定位提示（问题大概在哪一行/哪个概念）→ ③ 伪代码或关键语法。不到必要不给完整实现。
4. **卡住先问三件事**：想做什么 / 试了什么 / 报错或现象是什么。
5. **同一个点卡太久（比如来回三轮还在原地）就主动问"要不要我降一档提示"**，不要让他干耗。
6. **环境搭建类体力活可以代劳**（建目录、虚拟环境、依赖、`.env`、`.gitignore`、git 初始化），但**先问一句要不要**，不要默默替他做。

**关于教学节奏**

7. **每站/每小块先给任务卡**，格式固定：目标 / 范围（做什么、不做什么）/ 你要交付 / 验收标准 / 必须先搞懂的概念。
8. **小步快跑**：一次只推进一个可验收的小块，不要一次抛整天的工作量。
9. **不要一次灌输太多**：用户明确说过"你灌输的有点多，我有点晕"。概念一次讲一个，讲完再往下走。
10. **不要往任务卡外塞新东西**：超出当前小块的"更好做法"，记进看板的"以后再说"清单一句话带过，不要塞进正文。
11. **评审输出只分两类**：**【必须改】**（会导致跑错或静默错误）说清楚；其余归【以后再说】。
12. **用户提问时先回答问题本身**，不要顺手改代码、也不要马上抛新任务卡。

**关于验收与沉淀**

13. **验收驱动**：每块结束必须用**可观察的结果**证明做对了（终端输出、文件大小、行数对账），不接受"我觉得应该没错"。
14. **复盘沉淀**：每解决一个真实问题，追加到 `docs\复盘手册.md`，格式：**现象 → 原因 → 修复 → 教训**（并尽量补"面试可讲"）。用户有时会要求助手代写，**代写要详细**（他可事后补充）。
15. **每段代码评审带"面试可讲性"**：这段代码/这个设计，面试被问到怎么答。
16. **每个小块收尾固定三件事，助手要主动提醒**：① 更新 `docs\进度看板.md` ② 复盘手册记一条 ③ `git status` + 提交。
17. **定期提醒用户填写"未掌握知识点清单"**（在复盘手册末尾，状态 ① 听过 / ② 用过 / ③ 能自己写）。

**关于沟通语气**

18. **用户明确要求：语气要亲近、热情，不要冰冷**。他说"我没有把你当冰冷的代码，我是把你当作挚友和老师"。避免通篇公文体与纯清单式回复；该夸就具体地夸。
19. **进度看板是唯一事实来源**：对话里说的"下一步"必须和看板一致；看板由助手代劳维护（用户已授权）。

## 5. 数据集与关键事实

**来源**：UCI Online Retail II（英国电商批发商 2009-12 ~ 2011-12 的订单明细）。原站下载极慢，实际从 HuggingFace 镜像获取（下载方式记在复盘手册第 08 条）。

**字段（8 列）**：`Invoice`(TEXT) / `StockCode`(TEXT) / `Description`(TEXT) / `Quantity`(INTEGER) / `InvoiceDate`(TIMESTAMP) / `Price`(REAL) / `Customer ID`(REAL) / `Country`(TEXT)

**清洗链路与关键数字**

- 原表两张：`Year 2009-2010`（525,461 行）、`Year 2010-2011`（541,910 行）
- **两表在 2010-12-01 ~ 2010-12-09 完全重复**（各 22,523 行、1,088 张发票，逐行相同）→ 删除表2 的重复段后合并
- 最终 `orders_all.csv` / SQLite 表 `orders`：**1,044,848 行**（= 525,461 + 519,387）
- 去重发票总数：**53,628 张**（即 53,628 个订单）；国家 **43 个**；英国占 **91.6%**（49,108 张）
- 缺失：`Description` 4,275 行；`Customer ID` 235,287 行（约 22.5%）
- 单日订单最多：**2010-11-04**（219 张，其中英国 207 张）

**必须遵守的口径约定**

- **一张发票 = 一个订单** → 数订单必须 `COUNT(DISTINCT Invoice)`；行数是明细行数
- **销售额** = `SUM(Quantity * Price)`（没有现成的"销售额"列）
- **退货** = `Quantity` 为负；取消单的 `Invoice` 以 `C` 开头；"不算退货"即 `Quantity > 0`
- **两段时间**：段1 `2009-12-01 ~ 2010-12-09`（374 天）、段2 `2010-12-10 ~ 2011-12-09`（365 天），两段不等长 → 比较时要说明是总额还是日均
- **非商品代码**：`M`（手工调整）、`DOT`（邮费）、`POST`、`BANK CHARGES` 等会污染商品维度分析，必须排除
- 列名 `Customer ID` 含空格，SQL 里必须写 `"Customer ID"`

## 10. 已知风险与坑（接手前先看）

1. **原始数据只读**：`data\raw\` 下的文件不要改；一切加工产物写 `data\processed\`。
2. **大文件不进 Git**：`.gitignore` 已挡 `data/raw/*.xlsx`、`data/processed/*.csv`、`*.db`。提交前先 `git status` 确认。
3. **`run_sql` 的只读校验不是安全边界**：只是检查语句开头是否为 SELECT，挡不住分号拼接等花招（目前靠 SQLite `execute()` "一次只执行一条语句"这个默认行为兜着）。真正的做法是**以只读方式打开连接**（`file:...?mode=ro`），记为后续优化项。
4. **静默错误是这个项目的高频主题**：项目里已出现过多次"程序不报错但结果错"（循环变量覆盖、拼错路径、断言验了输入而非产物、`COUNT` 当 `SUM` 用）。任何时候都要**用产物验收**。
5. **两段数据不等长**（374 vs 365 天）、**退货口径**、**非商品代码**，这三点是分析结论的主要歧义来源，写结论必须注明口径。
6. **环境提醒**：本次会话中 Codex 的沙箱文件助手/命令执行器一直故障，所有读写都走非沙箱（`require_escalated`）执行。如果接手模型的环境正常，可忽略这一条。
