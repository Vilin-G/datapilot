# SQL 验收（第一站）

> **用途**：第一站的验收材料——**手写 SQL 回答业务问题**。
> 这些 SQL 之后会成为第四站评测集的标准答案，所以每条都留全。
> **数据库**：`data\processed\datapilot.db`，表 `orders`（1,044,848 行 × 8 列）
> **订单口径**：一张发票 = 一个订单，所以要数订单时必须 `COUNT(DISTINCT Invoice)`

---

## Q1 · 每个国家有多少张订单（去重）

**难度**：简单　**涉及字段**：`Country`, `Invoice`

```sql
SELECT Country, COUNT(DISTINCT Invoice) AS invoice_count
FROM orders
GROUP BY Country
ORDER BY invoice_count DESC;
```

**结果**（共 43 个国家，这里贴前几行）：

| Country | invoice_count |
| --- | --- |
| United Kingdom | 49108 |
| Germany | 1095 |
| EIRE | 806 |
| France | 746 |
| Netherlands | 250 |
| Spain | 188 |
| Belgium | 183 |
| … | … |
| Bermuda | 1 |

**解读**：43 个国家里，英国占 49,108 / 53,628 ≈ **91.6%** 的订单量，第二名德国只有 1,095 张，相差约 45 倍。说明这份数据的主体是一家**英国本土批发商**，其他市场都是零头。后续做国家维度的对比分析时，要意识到样本严重向英国倾斜——其他国家得出的结论可信度较低。

**交叉验证（两个独立口径对上了）**：

- `GROUP BY Country` 得到 43 行，与 `SELECT DISTINCT Country FROM orders` 的 43 个一致
- 43 个国家的订单数**加总 = 53,628**，与 `SELECT COUNT(DISTINCT Invoice) FROM orders` 的结果完全一致 → 同一张发票不会跨国家，按国家统计订单是可靠的

## Q4 · 哪一天订单最多（按天）

**难度**：中等　**涉及字段**：`InvoiceDate`, `Invoice`

```sql
SELECT DATE(InvoiceDate) AS day, COUNT(DISTINCT Invoice) AS order_count
FROM orders
GROUP BY day
ORDER BY order_count DESC
LIMIT 1;
```

**结果**：

| day | order_count |
| --- | --- |
| 2010-11-04 | 219 |

**解读**：2010-11-04 单日 219 张订单。全表 53,628 张订单 ÷ 约 740 天 ≈ 日均 72 张，所以这天是平均水平的 **3 倍**，属于明显高峰。结合这是英国批发商的数据，符合**圣诞采购季前的备货高峰**——后续做月度分析时，11 月大概率是全年高点。

**技术要点**：`InvoiceDate` 存的是 `2009-12-01 07:45:00` 这种带时间的值，按天分组前必须先用 `DATE(...)` 截成日期；订单数同样要 `COUNT(DISTINCT Invoice)`。

### Q4 补充 · 冠军日的国家构成

**目的**：只看总数会误判——要知道这 219 张订单是谁贡献的。

```sql
SELECT Country, COUNT(DISTINCT Invoice) AS order_count
FROM orders
WHERE DATE(InvoiceDate) = '2010-11-04'
GROUP BY Country
ORDER BY order_count DESC;
```

**结果**：

| Country | order_count |
| --- | --- |
| United Kingdom | 207 |
| Germany | 4 |
| Australia | 2 |
| EIRE | 2 |
| Spain | 2 |
| Japan | 1 |
| Lithuania | 1 |

合计 **219** ✓ 与 Q4 总数一致（交叉验证通过）

**解读**：冠军日里英国占 **207 / 219 ≈ 94%**。也就是说，"2010-11-04 是订单高峰日"这句话，**实际上是"英国在这天是高峰"**——只看总数会把一个局部现象当成全球规律。**拆维度的价值就在这里。**

**踩坑记录（写给未来的自己）**：

- 一开始用子查询把两步合成一句（先找出冠军日，再按国家拆解）。它跑通了，但有两个隐患：
  1. 子查询里没写 `LIMIT 1`——现在能跑是因为 **SQLite 在需要单个值的场合会隐式取第一行**，这是数据库宽容，不是可靠写法，换个数据库可能直接报错；
  2. 合在一起后不好调试，出错时分不清是哪一步的问题。
- **拆成两句简单 SQL，结果完全一样。会拆比会合重要**：拆开的版本更好读、更好调、也更好讲。

## Q5 · 某件商品两段时间的销售额对比（退货不计）

**难度**：难（复合）　**涉及字段**：`StockCode`, `InvoiceDate`, `Quantity`, `Price`

**题目原文**：某件商品对比销售情况，销售额是否提升？（退货不算销售额；09到10年为一个时间段，10到11年为一个时间段）

**口径**：

- 时间分段：`2009-12-01 ~ 2010-12-09`（374 天）与 `2010-12-10 ~ 2011-12-09`（365 天）
  - 起点是 12-10 而不是 12-01：那 9 天在两张原表里重复，合并时已删除
- 销售额 = `SUM(Quantity * Price)`，且只统计 `Quantity > 0`（退货不计）
- 商品用 `StockCode` 定位，不用 `Description`（文本会改会错）

**对比对象**：`StockCode = '22423'`

挑选过程：先按 `SUM(Quantity * Price)` 找出销售额最高的商品，结果前三名是 `M`（手工调整）、`22423`（真商品）、`DOT`（邮费）——**只有 22423 是商品**，取它作为对比对象。这一步说明：不做数据清洗，"最畅销商品"的榜单就是垃圾。

**SQL（两段各跑一次）**：

```sql
-- 第一段：2009-12-01 ~ 2010-12-09
SELECT SUM(Quantity * Price) AS sales_seg1
FROM orders
WHERE StockCode = '22423'
  AND Quantity > 0
  AND InvoiceDate >= '2009-12-01'
  AND InvoiceDate <= '2010-12-09 23:59:59';
```

```sql
-- 第二段：2010-12-10 ~ 2011-12-09
SELECT SUM(Quantity * Price) AS sales_seg2
FROM orders
WHERE StockCode = '22423'
  AND Quantity > 0
  AND InvoiceDate >= '2010-12-10'
  AND InvoiceDate <= '2011-12-09 23:59:59';
```

**结果**：

| 时间段 | 销售额 | 天数 | 日均 |
| --- | --- | --- | --- |
| 段1 · 2009-12-01 ~ 2010-12-09 | 170,078.51 | 374 | 454.75 |
| 段2 · 2010-12-10 ~ 2011-12-09 | 161,005.76 | 365 | 441.11 |

**结论**：

- 总额口径：`(161,005.76 − 170,078.51) / 170,078.51 ≈ **−5.3%**`
- 日均口径：`(441.11 − 454.75) / 454.75 ≈ **−3.0%**`
- **销售额没有提升，小幅下降。** 两个口径方向一致，但幅度不同——**写结论时必须说明用的是哪个口径**，否则别人复现不出你的数字。

**解读的尺度**：3~5% 对这个商品属于温和波动（它两段都稳定在 16~17 万），**不足以断言"趋势性下滑"**；要下这个判断，得看更细的月度曲线，而不是两个点。

**过程记录**：

- **退货口径的影响不小**：含退货时第一段是 163,051.46，排除退货后是 170,078.51，差 7,027（约 4%）
- **两段天数不等**（374 vs 365）：直接比总额对段2 不公平，所以额外算了日均
- **非商品代码**（`M` / `DOT` / `POST`）会污染排行榜，做商品维度分析前必须排除
